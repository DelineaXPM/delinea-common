delinea-common end-to-end tests
===============================

The default suite (go test ./...) is fully offline and deterministic. Live
tests are built only with the e2e tag:

  go test -tags e2e ./...

By default, each live test skips when its fixtures are absent. Set
DELINEA_COMMON_TEST_REQUIRE_E2E=1 (or run make e2e-strict) to make every required
fixture absence fail; the scheduled workflow uses this mode so missing
environment secrets cannot turn a green run into an empty run. The strict suite
requires every fixture listed below, including its dedicated attachment secrets.

The scheduled/manual workflow runs the live suite serially on Ubuntu, macOS,
and Windows. Its credentials are environment secrets in the live-tests
environment, which accepts only main. A manual run against another branch
therefore cannot receive live credentials. Overlapping workflow runs are
queued, and the OS matrix permits only one runner at a time, so shared tenant
fixtures are not exercised concurrently by this repository.

The tests never print secret values: assertions compare lengths, status codes,
or a configured SHA-256 digest. Point the fixtures at throwaway test objects,
not production ones. In CI, store them as live-tests environment secrets.

The live tests span both server-facing packages:
  - api/e2e_test.go              the token engine and raw REST calls
  - secrets/e2e_test.go          the secrets library (New + Resolve by ID/path,
                                 including attachment download)

Both share one fixture set, keyed by target. Common's fixtures use the
DELINEA_COMMON_TEST_* prefix; the consuming CLI repository has its own
DELINEA_TOOLS_TEST_* contract.

SECRET SERVER FIXTURES
----------------------

  DELINEA_COMMON_TEST_SS_URL          base URL of a Secret Server or SSC tenant
  DELINEA_COMMON_TEST_SS_USERNAME     local user with API access
  DELINEA_COMMON_TEST_SS_PASSWORD     its password
  DELINEA_COMMON_TEST_SS_SECRET_ID    numeric id of a secret to read
  DELINEA_COMMON_TEST_SS_SECRET_PATH  folder path of that same secret, backslash
                                   delimited with a leading backslash, exactly as
                                   /api/v1/folders/<id> reports it in folderPath,
                                   followed by the secret's name — for example
                                   \ci\database\prod. Required by the strict suite;
                                   local runs skip the path cases without it
  DELINEA_COMMON_TEST_SS_SECRET_FIELD field slug to read
  DELINEA_COMMON_TEST_SS_SECRET_VALUE expected value of that field (the assertion)
Attachment fixtures:

  DELINEA_COMMON_TEST_SS_FILE_SECRET_ID     id of a secret with a file field
  DELINEA_COMMON_TEST_SS_FILE_SECRET_FIELD  slug of that file field
  DELINEA_COMMON_TEST_SS_FILE_SHA256        hexadecimal SHA-256 of its downloaded bytes

Exercised: backend probing and target inference; the password grant; rejection
of a deliberately invalid bearer token with HTTP 401; self-expiration of a
disposable cached token and recovery from Secret Server's exact expired-token 403;
GET /api/v1/users/current; validation and reuse of a pre-obtained token; the
secrets library resolving the fixture by id and @path; an id read carrying a
non-sensitive autoComment audit value; and attachment fixtures that verify eager
file downloads byte-for-byte via SHA-256.

PLATFORM FIXTURES
-----------------

  DELINEA_COMMON_TEST_PLATFORM_URL            platform tenant URL
  DELINEA_COMMON_TEST_PLATFORM_CLIENT_ID      service-identity client_id
  DELINEA_COMMON_TEST_PLATFORM_CLIENT_SECRET  its client_secret
  DELINEA_COMMON_TEST_PLATFORM_SECRET_ID      id of a secret readable via the vault
  DELINEA_COMMON_TEST_PLATFORM_SECRET_PATH    folder path of that same secret (see the
                                           Secret Server note above)
  DELINEA_COMMON_TEST_PLATFORM_SECRET_FIELD   field slug to read
  DELINEA_COMMON_TEST_PLATFORM_SECRET_VALUE   expected value of that field (the assertion)
Attachment fixture:

  DELINEA_COMMON_TEST_PLATFORM_FILE_SECRET_ID     id of a secret with a file field
  DELINEA_COMMON_TEST_PLATFORM_FILE_SECRET_FIELD  slug of that file field
  DELINEA_COMMON_TEST_PLATFORM_FILE_SHA256        hexadecimal SHA-256 of its downloaded bytes

Exercised: backend probing and target inference; the client-credentials grant;
rejection of a deliberately invalid bearer token with HTTP 401;
pre-obtained-token validation and reuse; vault discovery via the broker;
vault routing of GET /api/v1/secrets/<id> to the discovered vault; and the
secrets library resolving fixtures by id and path through that vault. The
additional fixtures cover attachment download. The Platform suites
construct an explicit api.TargetPlatform configuration; the fixtures carry only
the tenant URL and client credentials.

The _PATH fixtures must name the same secret as the corresponding _ID fixture,
so both resolve to the same _VALUE. That is deliberate: it asserts the two
reference forms agree, and needs no second expected value.

Example (Platform):

  export DELINEA_COMMON_TEST_PLATFORM_URL=https://<tenant>.delinea.app
  export DELINEA_COMMON_TEST_PLATFORM_CLIENT_ID=<client-id>
  export DELINEA_COMMON_TEST_PLATFORM_CLIENT_SECRET=<client-secret>
  export DELINEA_COMMON_TEST_PLATFORM_SECRET_ID=1
  export DELINEA_COMMON_TEST_PLATFORM_SECRET_PATH='\folder\Secret Name'
  export DELINEA_COMMON_TEST_PLATFORM_SECRET_FIELD=Password
  export DELINEA_COMMON_TEST_PLATFORM_SECRET_VALUE=<expected-value>
  go test -tags e2e ./...

NOT COVERED / CACHE
-------------------

The interactive login flow is not covered by e2e: its out-of-band challenge
needs a human with a mailbox. Its state machine is
covered by offline unit tests against a fake Identity API. The token-cache
tests use an in-memory cache; nothing is written to disk.
